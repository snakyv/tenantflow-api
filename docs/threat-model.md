# Threat model

This document records the main trust boundaries and security assumptions for TenantFlow. It is intentionally scoped to the current modular-monolith architecture rather than attempting to be a complete enterprise security assessment.

## Assets

- organization-owned project, task, file and audit data;
- user credentials, access tokens and refresh-token secrets;
- webhook signing secrets and Stripe webhook secrets;
- object-storage keys and attachment metadata;
- billing/subscription state;
- background-job integrity.

## Trust boundaries

```text
Internet client
    |
    | HTTPS in deployment
    v
FastAPI API ----------------------> Stripe API
    |                                  |
    |                                  | signed events
    v                                  v
PostgreSQL                         Stripe webhook endpoint
    |
    +--------> Redis <-------- Celery worker
    |
    +--------> S3-compatible object storage

Celery worker --------------------> customer webhook endpoints
             --------------------> SMTP provider / Mailpit locally
```

PostgreSQL is the durable source of truth. Redis is treated as coordination infrastructure, not authoritative business storage.

## Primary threats and mitigations

### Cross-tenant data access

**Threat:** an authenticated user learns another tenant's resource UUID and attempts to read or mutate it.

**Mitigations:** tenant-owned routes include explicit organization context; membership is resolved server-side; resource queries include `organization_id`; database constraints prevent selected cross-tenant references; security/integration tests exercise isolation behavior.

### Privilege escalation

**Threat:** a member or viewer invokes owner/admin-only operations.

**Mitigations:** centralized permission checks map organization roles to explicit permissions. Ownership-changing and billing operations require owner-level permission.

### Credential theft and replay

**Threat:** stolen access or refresh tokens are reused.

**Mitigations:** access tokens are short-lived and audience/issuer validated. Refresh tokens are random values stored only as SHA-256 fingerprints, rotated on use and revocable. Production requires non-default application secrets.

### Duplicate side effects

**Threat:** network retries create duplicate organizations, invitations, checkout sessions or payment-event processing.

**Mitigations:** PostgreSQL-backed idempotency keys protect selected write operations; conflicting payload reuse is rejected; concurrent ownership is resolved with database uniqueness/locking; Stripe receives an idempotency key; Stripe events are deduplicated under a unique event ID.

### Webhook forgery

**Threat:** a receiver cannot distinguish TenantFlow webhook deliveries from forged requests, or an attacker forges Stripe events.

**Mitigations:** outbound deliveries are HMAC-SHA256 signed with per-endpoint secrets. Stripe webhook requests are verified against the raw request body and configured endpoint secret before business processing.

### Server-side request forgery through outbound webhooks

**Threat:** a tenant registers loopback, private, link-local or otherwise non-public destinations and uses TenantFlow to probe internal services.

**Mitigations:** production registration resolves and validates webhook targets, and workers repeat target validation immediately before delivery. Private targets are permitted only through an explicit development/test configuration switch.

**Residual risk:** DNS rebinding and complex proxy/network topologies require infrastructure-level egress controls for stronger production guarantees. Application validation is defense in depth, not a replacement for network policy.

### File/object-key abuse

**Threat:** user-controlled filenames become filesystem/object paths or tenants access each other's object metadata.

**Mitigations:** object keys are generated by the server using tenant IDs and random UUIDs; user filenames are metadata only; allowed media types and declared sizes are validated; attachment records carry tenant ownership; upload/download URLs are short-lived pre-signed operations.

**Residual risk:** production deployments that accept untrusted files should add malware/content scanning and verify actual uploaded object size/type after upload.

### Brute-force authentication

**Threat:** repeated login attempts target an account or API instance.

**Mitigations:** authentication throttling uses a Redis-backed atomic token bucket shared across API replicas and returns `429` when exhausted.

### Secret disclosure through logs

**Threat:** credentials, tokens or signing secrets are copied into operational logs.

**Mitigations:** request logging records correlation and request metadata but not authorization headers, password bodies, JWTs or application secrets. Production logging is structured for safer downstream processing.

### Background-job loss or duplication

**Threat:** API/worker failure causes durable work to disappear or execute more than once.

**Mitigations:** durable work uses Celery rather than in-process FastAPI background tasks; tasks are designed to tolerate retries where required; broker publication failure rolls back the API write transaction.

**Residual risk:** database commit and broker publication are not an atomic transaction. The current boundary is documented in ADR 0005. A transactional outbox is the intended next step if exactly-once publication guarantees become a product requirement.

## Deployment assumptions

The repository does not claim that application controls alone make an Internet deployment secure. A real production environment should additionally provide TLS termination, secret management, database/Redis network isolation, object-storage access controls, container/image scanning, egress restrictions for webhook workers, backups, monitoring/alerting and an incident-response process.

## Security verification

The repository includes focused unit/security tests and infrastructure-dependent integration tests for critical behavior. `SECURITY.md` describes reporting and operational guidance, while `VALIDATION.md` distinguishes checks executed during artifact construction from checks that still require the target Docker/GitHub environment.
